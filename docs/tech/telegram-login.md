# Вход через Telegram (ТЗ 003-f)

Миграция `supabase/migrations/20261128100000_telegram_login.sql`, Edge Function `supabase/functions/telegram-auth`,
клиент `src/auth/telegram.ts` + `src/auth/AuthProvider.tsx`, тест `supabase/tests/rls_003f_telegram.sql`.

## Поток
1. **Кнопка «Войти через Telegram»** — наша, по макету (без стандартного виджета). Нажатие уводит браузер на
   `https://oauth.telegram.org/auth?bot_id=<VITE_TELEGRAM_BOT_ID>&origin=<сайт>&return_to=<сайт>/me-wish/`.
   Telegram проверяет, что `origin` совпадает с доменом бота (`/setdomain` → `91dovzhenko.github.io`); на других адресах, в том числе localhost, он отвечает «Bot domain invalid».
2. Пользователь вводит номер и подтверждает вход в приложении Telegram. Telegram возвращает его на `return_to` с
   `#tgAuthResult=<base64 JSON>`: `id, first_name, last_name, username, photo_url, auth_date, hash`.
   `return_to` — корень приложения: там есть `index.html`, переход через `404.html` не нужен.
3. `readTelegramCallback()` при загрузке (до роутера) забирает данные из адреса и чистит строку. Экран входа показывает «Входим…» (`status = 'exchanging'`).
4. `exchangeTelegram()` отправляет данные в Edge Function **`telegram-auth`** (POST).
5. Функция:
   - принимает только поля Telegram (лишнее поле — 400);
   - проверяет подпись: `secret = SHA256(TELEGRAM_BOT_TOKEN)`, `hash = hex(HMAC_SHA256(secret, data_check_string))`, где data_check_string — все поля, кроме `hash`, «ключ=значение» по алфавиту через `\n`. Сравнение без утечки по времени. Неверно — 401 `bad_signature`;
   - проверяет свежесть: `auth_date` не старше 5 минут и не больше чем на минуту в будущем. Иначе — 401 `expired`;
   - ищет аккаунт: профиль с этим `telegram_id`, у пользователя которого служебная почта `telegram-<id>@me-wish.invalid` (домен `.invalid` зарезервирован, письма никуда не уходят);
   - если аккаунта нет — создаёт пользователя Admin API (`email_confirm: true`, `user_metadata.full_name` = «Имя Фамилия», `avatar_url` = фото Telegram). Профиль и «Мои желания» создаёт триггер первого входа. `profiles.telegram_id` функция ставит сама: Supabase добавляет `app_metadata` уже после вставки пользователя, и триггер его не видит (это нашла самопроверка);
   - выпускает одноразовый токен входа: `auth.admin.generateLink({ type: 'magiclink', email })` → `properties.hashed_token`. Письмо не отправляется.
6. Браузер меняет токен на обычную сессию: `supabase.auth.verifyOtp({ token_hash, type: 'magiclink' })`. Дальше всё как при входе через Google: RLS, профиль, списки, обновление токена.

**В браузер попадает только одноразовый `token_hash`** (живёт до первого использования, повторно не принимается — проверено). Ключ `service_role` и токен бота остаются на сервере.

## Защита
- **`telegram_id` ставит только сервер.** Клиенту оставлено право менять в профиле только `display_name, avatar_url, avatar_path, default_list_id` (column grants). Иначе можно было бы вписать себе чужой `telegram_id`, и будущий вход этого человека через Telegram открыл бы чужой аккаунт.
- **`telegram_id` уникален** (частичный уникальный индекс): один Telegram — один аккаунт, даже при одновременном первом входе с двух устройств.
- **Почте одной не доверяем.** Включена обычная регистрация по почте (для Google она не нужна, но выключить её — менять настройки Auth). Кто-то мог бы заранее зарегистрировать `telegram-<чужой id>@me-wish.invalid` с паролем. Поэтому вход выдаётся только аккаунту, у профиля которого этот `telegram_id`. Если почта занята чужой регистрацией — 409 `account_conflict`, вход не выдаётся.
- **Функция без проверки JWT** (`verify_jwt = false`): её вызывают до входа, сессии ещё нет. Всё решает подпись Telegram.
- **GET** на функцию отдаёт `{ bot_id }` — публичную часть токена. Это проверка, что секрет на месте.

## Ответы функции
| Код | Тело | Когда |
|---|---|---|
| 200 | `{ token_hash, new_user }` | подпись верна, данные свежие |
| 400 | `bad_request` | лишнее поле, нет `id` или `auth_date` |
| 401 | `bad_signature` | подпись не сходится (подделка, изменённые поля, нет `hash`) |
| 401 | `expired` | `auth_date` старше 5 минут |
| 409 | `account_conflict` | служебная почта занята чужой регистрацией |
| 500 | `server` / `not_configured` | ошибка Admin API / нет `TELEGRAM_BOT_TOKEN` |

Приложение на любой ошибке показывает «Не получилось войти. Попробуйте ещё раз». «Попробовать ещё раз» повторяет тот способ входа, которым входили (`lastMethod`, хранится в `localStorage`).

## Отказ в Telegram
«Отмена» на странице Telegram пытается закрыть окно (`window.close()`). Если вкладку открыл сам пользователь, браузер её не закроет. Тогда пользователь возвращается кнопкой «Назад», и экран входа снова показывает кнопки (обработчик `pageshow`). Если Telegram вернёт `#tgAuthResult` без данных или с испорченными данными, это считается отказом — экран ошибки.

## Секреты и переменные
| Что | Где | Публичное? |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | Supabase → Edge Functions → Secrets | **нет**, только там |
| `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` | Supabase передаёт функции сам | нет |
| `VITE_TELEGRAM_BOT_ID` (`9170631172`) | `.env` локально; GitHub → Actions variables | да, часть токена до двоеточия |
| `VITE_TELEGRAM_BOT_NAME` (`me_wish_bot`) | `.env` локально; GitHub → Actions variables | да (пригодится на этапе 3) |

Проверка, что токена нет в сборке: `grep -r -E "[0-9]{8,10}:[A-Za-z0-9_-]{30,}" dist` — пусто (в сборке есть только публичный id бота).

## Аккаунты Google и Telegram
До этапа 3 (D-083, D-109) это **разные аккаунты**: аккаунт Telegram опознаётся по `telegram_id`, аккаунт Google — по Google. Ничего не объединяется. В «Способах входа» у аккаунта Telegram — «Telegram», у аккаунта Google — «Google».

## Как проверено
- **Самопроверка на сервере** (временная Edge Function, после проверки удалена): тестовые данные подписаны токеном бота на сервере, токен наружу не уходил. Результаты:
  - первый вход — 200, `new_user: true`; сессия получена;
  - профиль «Тест Самопроверка», `telegram_id` записан, список по умолчанию — «Мои желания»;
  - повторный вход тем же id — 200, `new_user: false`, **тот же пользователь**;
  - повторное использование `token_hash` отклонено;
  - клиент не может поставить себе `telegram_id`;
  - изменённое имя при той же подписи — 401 `bad_signature`; поддельный hash — 401; `auth_date` 10 минут назад — 401 `expired`; лишнее поле — 400; без hash — 401;
  - тестовый пользователь удалён.
- `rls_003f_telegram.sql` — 6/6: первый вход с данными Telegram, имя не берётся из служебной почты, уникальность `telegram_id`, клиент не меняет `telegram_id`, остальные поля профиля менять можно, чужой профиль не виден.
- Экран входа в браузере (заглушка Supabase): кнопка активна и уводит на `oauth.telegram.org` с правильными параметрами; с адресом `91dovzhenko.github.io` Telegram показывает «Войдите… для 91dovzhenko.github.io и ME:WISH». Возврат с поддельными данными — экран ошибки, «Попробовать ещё раз» снова ведёт в Telegram. Возврат с принятыми данными — «Входим…» → главная. Кириллица в имени разбирается правильно. В профиле — «Telegram, Вход выполнен через него».
- **На настоящих устройствах не проверено** — вход работает только на `91dovzhenko.github.io`, то есть после выкладки.

## Риск: установленное приложение на iPhone
В режиме standalone iOS может открыть `oauth.telegram.org` (другой сайт) во встроенном окне Safari. Обычно после возврата на наш адрес вход продолжается в самом приложении. Если на каком-то устройстве сессия окажется во встроенном окне, а не в приложении, запасной вариант — вход через бота: ссылка `t.me/me_wish_bot?start=…` и одноразовый код. Он требует вебхука бота (этап 3).
