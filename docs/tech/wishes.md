# Желания и фото (ТЗ 003-c)

Миграция `supabase/migrations/20261124200000_wishes_add_photos.sql`, тест `supabase/tests/rls_003c_wishes.sql`.

## Добавление желания — `add_wish()`
- `add_wish(p_wish_id, p_list_id, p_title, p_price, p_source_url, p_description, p_priority, p_image_path)` → uuid.
- **security invoker**: действуют обычные политики (`wishes` от своего имени; `list_items` — редактор, список не удалён, `can_link_wish`). Оба insert в одной транзакции: если появление в списке не создалось (чужой/удалённый список), желания тоже нет (проверено тестом).
- Проверки: название 1–200 символов (обрезается по краям), цена 0…999 999 999, приоритет 1–5, описание до 2000, ссылка `http(s)://` до 2048, `p_image_path` должен быть `<любая папка>/<p_wish_id>.<ext>` (папку проверяет триггер, см. ниже).
- `p_wish_id` задаёт клиент (`crypto.randomUUID()`), потому что фото загружается **до** сохранения, под этим id.
- Прямые insert в `wishes`/`list_items` по-прежнему разрешены политиками (пригодятся в 003-d: «Переместить»). Новое желание приложение создаёт только через `add_wish`.

## Фото: хранение
- Бакет **`wish-photos`**, **не публичный**, лимит 2 МБ, только `image/webp` и `image/jpeg` (в него попадает только сжатая копия).
- Путь: **`<user_id>/<wish_id>.webp`** (или `.jpg`, если браузер не кодирует WEBP — Safari на iPhone). Формат пути проверяет `is_wish_photo_path()`.
- В `wishes.image_path` хранится этот путь. **Триггер `wishes_check_image_path`**: при вставке или смене `image_path` вошедший пользователь может сослаться только на файл **из своей папки**. Иначе можно было бы вписать в своё желание путь к чужому фото и прочитать его через политику чтения. Сервер (service role, этап 4) — без проверки.

### Политики `storage.objects` (бакет `wish-photos`)
| Действие | Кто |
|---|---|
| select | своя папка **или** `can_view_wish_photo(name)` — есть желание с этим `image_path`, которое пользователь видит (`can_view_wish` = участник списка, где оно лежит, включая корзину) |
| insert | только в свою папку и только правильное имя |
| update (перезапись) | `can_manage_wish_photo(name)` — своя папка, и файл ещё ни на что не ссылается **или** пользователь — редактор желания, которое на него ссылается |
| delete | то же `can_manage_wish_photo` |

Анониму бакет недоступен (политики только для `authenticated`).

### Показ — подписанные ссылки
- `src/lib/photos.ts` → `usePhotoUrls(paths)`: пакетно `createSignedUrls(paths, 3600)`, кэш в памяти, перевыпуск за 10 минут до конца срока (и по таймеру, пока экран открыт).
- Только что загруженное фото показывается из памяти (`rememberLocalPhoto` — object URL сжатого файла), без запроса к Storage.
- Почему подписанные ссылки, а не публичный бакет: фото видят только участники списка; ссылка живёт час.
- **Гостевой доступ (этап 4):** Edge Function с service role сможет выдать гостю подписанные ссылки на фото открытого списка — политики и пути под это не мешают.

### Загрузка
- `uploadPhoto()` — `XMLHttpRequest` в REST Storage (`POST /storage/v1/object/wish-photos/<path>`, токен пользователя, `x-upsert: true`) — ради прогресса загрузки (supabase-js его не отдаёт).
- Загрузка начинается сразу после обрезки, пока заполняется форма. «Добавить» неактивна, пока фото грузится или не загрузилось (есть «Повторить»).
- Повторная обрезка и «Другое фото» перезаписывают тот же путь; если сменился формат — старый файл удаляется.

### Мусор в Storage
- «Удалить фото», закрытие формы без сохранения, «Не сохранять» → файл удаляется сразу (`remove`), пока на него не ссылается желание.
- Если `add_wish` упал — форма остаётся открытой, файл не удаляется (можно нажать «Добавить» ещё раз). Закрыли форму — файл удаляется.
- Остаётся только случай «вкладку закрыли посреди заполнения». Такие файлы: в папке пользователя, ни одно желание на них не ссылается. **Чистка — в 003-e** вместе с очисткой корзины: Edge Function по расписанию (или при открытии корзины) удаляет через Storage API файлы `wish-photos` старше суток, на которые нет `wishes.image_path`. Напрямую из SQL удалять нельзя: у `storage.objects` триггер `protect_delete`.
- **Редактирование (003-d):** новое фото грузится под **новым** именем `<user_id>/<новый uuid>.webp|jpg` — сохранённое фото не трогается, пока не нажали «Сохранить». После успешного сохранения старый файл удаляется (`removePhoto`), закрытие без сохранения удаляет только новый. «Обрезать» у сохранённого фото скачивает сохранённый квадрат (`downloadPhoto`) и обрезает его — исходника большего размера у нас нет.
- На этапе 2 (общие списки) при смене фото чужого желания старый файл придётся удалять **до** смены `image_path` (после неё `can_manage_wish_photo` чужой файл не отдаст) — или оставлять уборке.

## Обработка фото в браузере (`src/lib/image.ts`)
- Принимаются JPG, PNG, WEBP, HEIC до 20 МБ (по типу файла, у файлов без типа — по расширению). Ошибки — тексты с макетов.
- **HEIC:** iPhone при выборе из галереи сам отдаёт JPEG; Safari на Mac открывает HEIC. Если браузер не смог открыть HEIC (Chrome/Firefox на компьютере) — ошибка «Этот браузер не открывает HEIC. Выберите JPG или PNG либо откройте в Safari». Библиотеку-конвертер не добавляли: `heic-to` весит ~26 МБ (распакованный пакет), лицензия LGPL, а случай редкий.
- «Фото маленькое» — длинная сторона исходника меньше 800 px.
- Сжатие: `canvas` → квадрат 800×800 (если вырезанный квадрат меньше 800 px — его размер, без растягивания), WEBP 0.85, в Safari на iPhone — JPEG 0.85. Прозрачность — на белом фоне. Поворот по EXIF браузер учитывает сам.

## Обрезка — `src/components/ImageCropper.tsx`
- Переиспользуемый: `shape="square" | "circle"` (круг — для аватара в 003-e), `initial` — прошлая рамка для повторной обрезки, `onDone(crop)` отдаёт квадрат в пикселях исходника.
- Состояние: масштаб 1…3 (1 — фото закрывает рамку целиком) и точка исходника в центре рамки; фото не может выйти из рамки.
- Телефон: перенос одним пальцем, щипок двумя (Pointer Events, `touch-action: none`). Компьютер: перетаскивание мышью, ползунок и «−/+», колесо мыши, щипок трекпада (в Chrome/Firefox — `wheel` с `ctrlKey`, в Safari — `gesturechange`; на iPhone жесты Safari игнорируются, там работают касания). Esc — отмена, Enter — «Готово».

- Только у своих маркетплейсов (у обычного магазина короткий параметр может что-то значить):
  - Яндекс Маркет: `cpc`, `sponsored`, `nid`, `ultima`, `ogV`, `bnplSelectedPlan`, `uniqueId`, `srcrr`, `rs`, `lr`, `clid`, `cpa`, `pp`, `track`, `text`, `hid`, `from`;
  - Ozon: `at`, `sh`, `asb`, `asb2`, `keywords`, `avtc`, `avte`, `avts`, `is_apparel_size_selected`, `miniapp`, `oos_search`, `from`, `from_sku`, `tab`;

## Шторка на телефоне (`FormWindow`)
- **Клавиатура** (все шторки): контейнер повторяет `visualViewport` (на iOS клавиатура не уменьшает окно), кнопка внизу — над клавиатурой, отступ под ней 12 px (`Mobile-Add-Keyboard`).
- **Активное поле над кнопкой** (003-c-fix): iOS сам прокручивает поле только до клавиатуры и не знает о нашей кнопке. Поэтому после фокуса (через 50/300/600 мс — клавиатура выезжает с анимацией), при каждом изменении `visualViewport` и при вводе (описание растёт) прокрутка шторки поправляется так, чтобы поле было выше кнопки с отступом 16 px.
- **Свайп вниз** (D-104): тянуть можно за ручку (зона 24 px сверху) и шапку всегда; за содержимое — только если оно и всё под пальцем прокручено до верха (иначе обычная прокрутка). Шторка едет за пальцем, фон бледнеет. Отпустили дальше min(160 px, 25 % высоты) или быстрее 0,5 px/мс — закрывается; иначе возвращается. Проп `dirty`: при введённых данных шторка возвращается и вызывается `onClose` — форма спрашивает «Не сохранять…?». Касания — `touchstart` (passive) / `touchmove` (non-passive, `preventDefault` только во время свайпа).
