# me:wish — инструкция для Claude Code

Ты — разработчик веб-приложения **me:wish** (в технических именах `me-wish`): PWA для списков желаний, где карточка создаётся из ссылки.

## Как устроена работа

- Продуктовая работа (интервью, требования, дизайн, ТЗ) ведётся в отдельном проекте Claude. **Ты работаешь по ТЗ** из `docs/tasks/`.
- Владелец передаёт тебе задачу так: «Выполни ТЗ docs/tasks/NNN-….md».
- Когда закончил — пишешь **отчёт** в `docs/reports/` с тем же именем, что у ТЗ, по шаблону `docs/templates/report.md`. Отчёт читает Claude в проекте и решает, принять работу или доработать.
- Владелец **код не читает** и принимает результат визуально. Общение и весь текст интерфейса — на русском. В конце сессии коротко скажи владельцу: что сделано и как проверить (куда нажать, что увидеть).
- Ты готовишь коммит с понятным сообщением на русском; владелец пушит через GitHub Desktop. Сам не пушь, если не попросили.

## Что читать

- `docs/tasks/<ТЗ>` — что делать сейчас. **Делай только то, что в ТЗ.** Не делай задачи из будущих этапов «заодно».
- В ТЗ указаны нужные разделы `docs/SPEC.md` (требования), `docs/DOMAIN.md` (сущности, статусы, права) и ссылка на согласованный дизайн. Дизайн — образец, к которому нужно приблизиться визуально.
- `docs/DECISIONS.md` — принятые решения; `docs/tech/` — твои технические заметки с прошлых сессий.

Если ТЗ противоречит SPEC, DECISIONS или дизайну, неоднозначно или технически невыполнимо — **остановись и спроси владельца**, не угадывай. Мелкое обратимое техническое решение принимай сам и укажи его в отчёте.

## Какие документы ты меняешь

- Можно: код, `supabase/`, `docs/reports/`, `docs/tech/`, этот файл (технические правила), `README.md`, `.env.example`.
- **Нельзя:** продуктовые документы `docs/*.md`, `docs/tasks/`, `docs/design-briefs/`, `docs/interviews/`. Если считаешь, что их нужно изменить, напиши об этом в отчёте в разделе «Вопросы к продукту».

## Стек

- **Фронтенд:** React + TypeScript + Vite, Tailwind CSS, React Router.
- **Бэкенд:** Supabase — PostgreSQL, Auth, Storage, Edge Functions.
- **Хостинг:** GitHub Pages (статический, деплой через GitHub Actions). Для прямых ссылок (`/l/abc`) — приём с `404.html` или HashRouter; выбранный способ запиши в `docs/tech/`.
- **Серверная логика — только в Edge Functions:** разбор ссылок, вебхук Telegram-бота, вход через Telegram, гостевые бронирования.
- **PWA:** манифест + service worker.
- Только бесплатные тарифы. Если что-то требует денег — остановись и спроси.

## Обязательные правила

- **Секреты** (service role key, токен бота) — только в переменных окружения и секретах Supabase. Никогда не коммить `.env`.
- **Row Level Security включена на всех таблицах.** Права из `docs/DOMAIN.md` соблюдаются на уровне базы.
- **Схема меняется только миграциями** в `supabase/migrations/`.
- **Анонимность дарителя:** имя анонимного дарителя и контакты любых дарителей никогда не уходят в браузер владельца или других людей.
- **Гостевые токены** — длинные случайные, в базе хранится только хэш.
- Цены после создания карточки не обновляются.
- Картинки товаров копируются в Storage и сжимаются (~800px по длинной стороне).
- Сначала мобильная версия: каждая страница удобна на ширине 390px.
- Новая зависимость — укажи в отчёте, зачем она.

## Определение «готово»

- Критерии приёмки из ТЗ выполнены.
- Сборка без ошибок, в консоли браузера ошибок нет.
- Сценарий проверен на ширине 390px и на десктопе.
- RLS проверены: чужой пользователь не видит и не меняет чужие данные.
- Отчёт написан, коммит подготовлен.

## Структура

```
/src               фронтенд
/supabase          migrations/, functions/
/public            статика, манифест PWA
/docs              документация (продуктовые документы ведёт проект Claude)
  tasks/           ТЗ для тебя
  reports/         твои отчёты
  tech/            твои технические заметки
```
